# Reproducibility guide

This repository separates **fixed manuscript inputs and archived outputs** from live API-based graph construction. External database services can change over time; therefore, exact reproduction of reported manuscript results should use the fixed processed files rather than assuming that a new API call will return byte-identical data.

## Current public coverage

Available:

- COBS implementation and algorithm registry;
- Streamlit analysis interface;
- generic identifier-file PPI batch runner;
- exact final breast-cancer score-900 GCC edge list (252 nodes, 729 edges) with validation metadata;
- DISGENET query-provenance record without redistribution of the original query export;
- fixed CORUM-derived score-900 GCC input (5,090 nodes, 37,942 edges);
- processed yeast STRING score-400, score-700, and score-900 networks;
- full yeast COBS parameter-search files for all three thresholds;
- final yeast score-900 comparative benchmark outputs;
- community, metric, centrality, visualization, enrichment, and hallmark-analysis source modules.

Still to be hardened in a future archival release:

- a dedicated consolidated CORUM benchmark entry point;
- a fully locked environment captured from the publication run environment;
- automated regression tests against fixed manuscript inputs;
- publication-linked software release/tag and article DOI after publication.

## Grid-search and comparative-benchmark outputs

Parameter-search metadata and comparative benchmark outputs come from separate evaluation stages. For yeast score 900, the selected COBS parameters and Shen modularity match across the two stages. Some secondary metrics, such as conductance or transitivity, can differ because the benchmark summary was generated by the comparative evaluation stage. For values reported in the manuscript comparison table, use `data/yeast/benchmark_score900/summary_metrics.csv` or `yeast_benchmark_results.xlsx`.

The same principle applies to publication-linked CORUM benchmark results supplied in Supplementary Data S1: use the fixed benchmark outputs for the manuscript comparison, not exploratory or legacy run files.

## Generic API-based reruns

The Streamlit application and generic batch runner can construct new STRING PPI graphs from user-supplied identifiers. Those modes are useful for new analyses, but they are not the authoritative method for reconstructing historical database responses after external services have changed.

For a new identifier-file run:

```bash
python scripts/batch_run_overlap_ppi_v7_generic.py \
  --input-file identifiers.txt \
  --dataset-label my_dataset \
  --species 9606 \
  --required-score 900 \
  --add-nodes 0 \
  --use-giant true \
  --include-cobs \
  --include-keys cobs \
  --timeout-sec 600 \
  --outdir outputs_ppi_batch
```

## Minimum provenance for new experiments

Record at least:

1. input filename and SHA-256 checksum;
2. source database/version or retrieval date;
3. node and edge counts before and after component filtering;
4. species/taxon;
5. STRING required score and `add_nodes` setting;
6. graph scope (full network or giant connected component);
7. algorithm key and all parameter values;
8. random seed, if supported;
9. timeout and post-processing settings;
10. Python/dependency/platform versions;
11. output files, runtime, status, and timestamp.

## Preserve provenance records

Execution manifests and run metadata are historical records. Do not rewrite their timestamps, parameter values, software versions, or original run-relative paths merely because files are reorganized later. Document file mappings separately instead.

## Environment capture for a future archived release

After installing and validating a clean environment that truly represents the publication workflow, capture it without replacing the human-maintained `requirements.txt`:

```bash
python --version
python -m pip freeze > environment-lock.txt
```

Do not create a publication lock file from an unrelated development environment.
